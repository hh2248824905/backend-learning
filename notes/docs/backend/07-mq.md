## 0. 这个模块要解决什么问题

**规划中的五条**

1. 什么业务**不该**同步做？上了队列一定更好吗？
2. 消息为什么会丢？生产者、Broker、消费者三个环节各自怎么防丢？
3. 消息重复投递几乎必然发生，消费者怎么做到幂等？
4. 消费者处理失败后怎么办？重试几次？重试还是失败呢？
5. 上队列的代价是什么？

## 2. 计划覆盖的知识点

### 2.1 三个适用场景

| 场景 | 说明 | 例子 |
|---|---|---|
| **异步解耦** | 主流程不等非核心逻辑 | 下单后发短信、发积分、写审计日志 |
| **削峰填谷** | 突发流量先进队列，消费者按自己的节奏处理 | 秒杀、批量导入 |
| **最终一致性** | 跨服务的分布式事务，用消息补偿 | 订单服务扣库存后通知库存服务 |

::: danger 不是所有「慢操作」都该上队列
**判断标准**：这个操作**失败了、丢了**，用户能接受吗？

| 操作 | 能上队列吗 |
|---|---|
| 发营销短信 | ✅ 丢了下次再发，或干脆不发 |
| 写操作日志 | ✅ 丢几条可以接受 |
| **扣库存** | ❌ 绝对不能丢 |
| **支付扣款** | ❌ 绝对不能丢 |
| **用户看到结果必要的操作** | ❌ 上队列会让接口返回了但数据还没好，前端要轮询 |

**上队列的代价**：系统复杂度上升一个数量级（要装 Broker、要处理积压、要监控死信、要保证幂等）。**能用同步解决的就别上队列。**
:::

### 2.2 核心模型

以 RabbitMQ 为例（RocketMQ/Kafka 概念类似，名词不同）：

```
生产者 Producer
    ↓ 发消息到 Exchange，带 RoutingKey
交换机 Exchange          ← 决定消息往哪个队列投
    ↓ 按类型 + 绑定规则路由
队列 Queue               ← 消息真正的存储位置，先进先出
    ↓ 投递给订阅了的消费者
消费者 Consumer
```

| 组件 | 职责 | 关键点 |
|---|---|---|
| **Exchange** | 路由决策 | 四种类型：`direct`（精确匹配 key）、`topic`（通配匹配）、`fanout`（广播给所有队列）、`headers`（按头匹配） |
| **Queue** | 存储 | 有容量上限，满了生产者会被阻塞或丢弃 |
| **Binding** | Exchange → Queue 的规则 | topic 类型支持 `*`（一个词）和 `#`（零或多个词） |
| **RoutingKey** | 路由键 | 生产者在消息上带的标识 |
| **VirtualHost** | 逻辑隔离 | 不同项目用不同 vhost，互不干扰 |

**`topic` 类型的通配示例**：

| RoutingKey 模式 | 匹配 | 不匹配 |
|---|---|---|
| `order.*` | `order.create`、`order.pay` | `order.create.success` |
| `order.#` | `order.create`、`order.create.success` | `user.create` |

### 2.3 消息不丢的三个环节

消息从生产到消费，**三个环节都可能丢**：

| 环节 | 丢的原因 | 防护手段 |
|---|---|---|
| **生产者 → Broker** | 网络抖动、Broker 没落盘 | ① 开启发送确认（Publisher Confirm）② 失败重试 ③ 本地消息表（业务库和消息表同事务） |
| **Broker 内部** | Broker 宕机，消息还在内存里 | ① 声明队列/交换机为持久化（durable）② 消息标记为持久化（`deliveryMode=2`）③ 镜像队列 / 集群 |
| **Broker → 消费者** | 消费者拿到消息后宕机，但已自动 ACK | **手动 ACK**：处理成功才确认；失败则 nack 让消息重新入队 |

::: tip 持久化三件套缺一不可
```java
// 1. 队列持久化
new Queue("order.queue", true);              // second param: durable

// 2. 消息持久化
MessageProperties props = MessageProperties.PERSISTENT_TEXT_PLAIN;

// 3. 确认模式：手动 ACK
// spring.rabbitmq.listener.simple.acknowledge-mode=manual
```

只做 1 不做 2，队列在但消息在重启后丢了。只做 1、2 不做 3，消费者崩了消息就没了。
:::

### 2.4 幂等消费

**前提认知**：在「消费者处理成功但 ACK 丢失」这种情况下，Broker 会重发消息 —— **至少投递一次（at-least-once）是常态，「恰好一次」几乎做不到**。

所以**消费者必须幂等**：同一条消息消费多次，业务结果不变。

| 方案 | 做法 | 适用 |
|---|---|---|
| **唯一索引** | 业务表加唯一约束，重复插入直接失败忽略 | 新增类操作，**最可靠** |
| **状态机判断** | 「只有待支付订单才能支付」，重复消息因状态不匹配被忽略 | 有状态流转的业务 |
| **去重表** | 消息 ID 存 Redis/数据库，处理前先查 | 通用，需额外存储 |
| **Redis SETNX** | `SETNX msgId` 成功才处理 | 高性能，但 Redis 挂了会失效 |

```java
// 唯一索引方案的典型写法
try {
    orderMapper.insert(order);
} catch (DuplicateKeyException e) {
    log.warn("订单已存在，忽略重复消息, orderNo={}", orderNo);
}
```

### 2.5 重试与死信

**消费者处理失败的完整链路**：

```
处理失败 → 按策略重试 → 重试 N 次仍失败 → 投递到死信队列（DLX）
                              ↓
                      人工介入 / 定时补偿任务
```

| 配置项 | 说明 |
|---|---|
| 重试次数 | Spring Boot 里 `spring.rabbitmq.listener.simple.retry.max-attempts`，一般 3 次 |
| 重试间隔 | 建议指数退避（1s、2s、4s），避免瞬间打爆下游 |
| 死信队列触发条件 | ① 被拒绝且不重回队列 ② 消息 TTL 过期 ③ 队列达到最大长度 |

::: warning 重试前要想清楚：这个失败是「可重试」的吗
| 失败原因 | 该重试吗 |
|---|---|
| 数据库连接超时 | ✅ 重试可能成功 |
| 下游服务 500 | ✅ 可能瞬时故障 |
| **消息格式错误（反序列化失败）** | ❌ 重试一万次也一样失败，只会堆积 |

**无脑重试会制造消息积压，把整个队列堵死。** 对不可重试的错误要直接进死信。
:::

### 2.6 与 06 模块的衔接

07 的代码会大量依赖 06 的 ORM 能力 —— 比如「本地消息表」方案：

```java
@Service
public class OrderService {

    @Transactional
    public void createOrder(Order order) {
        orderMapper.insert(order);                      // 06 的知识
        messageMapper.insert(new Message(order));        // 同一事务写消息表
    }
}
```

**两个表在同一个事务里写**，保证「业务成功 = 消息一定被记录」。再由定时任务扫描消息表投递到 MQ —— 这个「扫描投递」就是 08 的定时任务。

**07 和 08 是一对**：队列负责实时投递，定时任务负责补偿投递。

## 5. 关键决策（写笔记时要回答）

| 问题 | 可选方案 |
|---|---|
| 用哪个 MQ？ | RabbitMQ（易上手，管理台好）/ RocketMQ（阿里系，事务消息强）/ Kafka（吞吐最高） |
| 交换机类型 | `topic`（灵活，推荐）/ `direct`（简单明确）/ `fanout`（广播） |
| ACK 模式 | **手动 ACK**（默认的自动 ACK 会丢消息）/ 自动 |
| 幂等方案 | 唯一索引（最可靠）/ 去重表 / 状态机 |
| 重试策略 | 有限次重试 + 死信 / 无限重试（危险） |
| 消息体格式 | JSON（可读，跨语言）/ 二进制（性能好，难调试） —— **推荐 JSON** |

## 6. 预习要点

1. **消息队列不是银弹**：引入后要维护 Broker、监控积压、处理死信、保证幂等
2. **至少一次 vs 恰好一次**：前者可实现，后者工程上代价极高，所以设计时默认按「会重复」处理
3. **消息顺序性**：多消费者并发消费时，同一队列的消息顺序不保证。要保证顺序得让同一业务键的消息路由到同一队列
4. **积压的代价**：消息堆积会占满磁盘，Broker 会阻塞生产者，进而把上游服务拖死
